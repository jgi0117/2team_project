# Azure PdM + 조달·비용 시뮬레이션

이 프로젝트의 질문은 **“고장을 얼마나 잘 맞히는가?”에 더해 “실제 정비를 준비할 시간을 확보하면서 총비용을 줄일 수 있는가?”**입니다. 고장을 하루 전에 정확히 알아도 부품이 도착하는 데 42일이 걸린다면 생산중단을 피하기 어려울 수 있습니다.

## 데이터의 성격과 역할

Azure PdM은 Microsoft가 시뮬레이션으로 생성한 공개 예제 데이터입니다. 공개 데이터라는 사실이 실제 공장 실측 데이터라는 뜻은 아닙니다. 근거는 [Microsoft의 원문 노트북](https://github.com/microsoft/sqlworkshops/blob/master/SQLServerAndAzureMachineLearning/ML%20Services%20for%20SQL%20Server/notebooks/Predictive%20Maintenance%20in%20Python%20Notebook.ipynb)의 Problem Description입니다.

센서·Error·정비·고장·설비 정보는 공개 CSV에서 가져오고, 조달기간·재고·비용은 프로젝트 가정으로 따로 둡니다. `comp2`를 “R2R 설비 정밀 롤러 구동 모듈”로 부르는 것은 시나리오용 매핑이며 원본 부품의 실제 정체를 뜻하지 않습니다.

## 확보한 파일

저장 위치: `data/raw/azure_pdm/`. 행 수는 헤더를 제외한 실측 집계입니다.

| 파일 | 행 수 | 주요 컬럼 | 역할 |
| --- | ---: | --- | --- |
| PdM_telemetry.csv | 876,100 | datetime, machineID, volt, rotate, pressure, vibration | 시간별 센서 관측 |
| PdM_errors.csv | 3,919 | datetime, machineID, errorID | 비치명적 오류 이력 |
| PdM_maint.csv | 3,286 | datetime, machineID, comp | 부품 교체 이력 |
| PdM_failures.csv | 761 | datetime, machineID, failure | 부품별 고장 기록 |
| PdM_machines.csv | 100 | machineID, model, age | 설비 모델·연식 정보 |

센서 데이터 범위는 `2015-01-01 06:00:00`부터 `2016-01-01 06:00:00`까지입니다. 정비 이력은 `2014-06-01 06:00:00`부터 있어 관측 시작 전 마지막 교체 시점을 구하는 데 활용할 수 있습니다. 타임스탬프의 시간대는 확인되지 않았으므로 한국 시간으로 임의 변환하지 않습니다.

부품 고장 건수는 comp1 192건, **comp2 259건**, comp3 131건, comp4 179건입니다. 이는 독립적인 설비 정지 횟수가 아니라 부품 고장 행 수입니다. 전체 파일의 빈 필드와 검사 기준 중복 키는 0건입니다. 검사 범위와 SHA-256은 [검사 결과](../reports/tables/azure_pdm_profile.json)에 기록했습니다.

## 분석 구조

```text
Azure 공개 예제: 센서 + 과거 Error/정비/고장 + 설비 정보
    → 예측 시점까지의 정보로 특징 생성
    → 향후 7/14/30/42/60/90일 내 comp2 고장 확률
    → 확률 임계값을 적용해 경고·발주·정비 정책 실행
    → 별도 가정한 조달기간·재고·비용으로 운영 시뮬레이션
    → 동일 평가기간의 총비용과 실제 확보한 정비 준비시간 비교
```

시점 t의 horizon H 타깃은 같은 설비에서 `(t, t+H]` 안에 comp2 고장이 있으면 1입니다. 고장 시점 이후의 센서·정비 기록은 t의 입력에 포함하지 않습니다. 정비·오류 같은 이벤트 파일은 단순히 시간별 센서에 전부 조인하지 않고, t 이전 발생 횟수나 마지막 교체 이후 경과시간 등으로 집계합니다.

`P(42일 이내 고장)`은 **고장 42일 전에 경고한다는 보장이 아닙니다.** 내일 발생할 고장도 42일 타깃에 포함됩니다. 경고가 실제로 발생한 날짜와 고장 날짜의 차이, 재고 유무, 부품 도착일을 시뮬레이션에서 따로 추적해야 합니다.

## 운영조건 예시 — 측정값이 아닌 프로젝트 가정

| 항목 | 가정 |
| --- | --- |
| 제작 / 물류·통관 / 검사·정비준비 | 28일 / 7일 / 7일 |
| 총 대응기간 | 42일, 신규 조달이 필요한 경우 |
| 초기 예비재고 | 0개와 1개 시나리오를 각각 비교 |
| 예방교체 / 긴급교체 | 300만원/건 / 700만원/건 |
| 설비정지 손실 | 500만원/일 |
| 보유재고 비용 | 5만원/(개·일) |

재고가 이미 있으면 42일 전체가 필요한지, 검사·정비준비만 필요한지 별도로 정합니다. 발주 고정비와 부품 구매비는 아직 수치가 없으므로 추가 정의가 필요합니다. 교체비에 부품값이 포함되는지도 정해 비용 중복을 방지합니다.

총비용은 구매·발주비, 예방·긴급교체비, 설비정지 일수에 따른 손실, 보유재고 일수에 따른 비용 등을 합산합니다. 경고가 매시간 반복돼도 동일 부품에 중복 발주하지 않도록 진행 중 주문과 재고를 상태로 관리합니다. 예방교체 후 원래 고장이 회피되었다고 처리할지 등 관측되지 않은 결과는 시뮬레이션 가정으로 명시합니다. 원본 이력만으로 정책 변경의 실제 효과가 입증되지는 않습니다.

## 결과를 정해놓지 않는 평가

- 사용자 제안의 `F1 0.76 / 비용 0.7억 / 42일 최적`은 설명용 숫자이며 분석 결과가 아닙니다. 42일이 반드시 최적이어야 할 이유도 없습니다.
- Microsoft 원문 예제는 24시간 고장예측을 다룹니다. 42~90일의 예측 신호가 충분한지는 새로운 검증 과제입니다. 긴 조달기간에는 조기예측보다 안전재고가 유리할 수도 있습니다.
- 시간순으로 학습·검증·테스트를 나눕니다. 각 경계에서 학습 라벨의 미래 관측 구간이 다음 평가 구간에 겹치지 않게 제거합니다. 여러 horizon을 공정하게 비교하려면 최대 90일을 고려한 공통 평가 구간을 정합니다.
- 관측 종료 직전의 행은 미래 H일을 끝까지 보지 못합니다. 이런 행을 자동으로 정상(0) 처리하지 말고 제외하거나 중도절단 방식으로 처리합니다.
- F1뿐 아니라 확률 보정, 고장 사건별 사전경고 포착률, 오경보·발주 횟수, 경고부터 고장까지의 시간, 다운타임, 총비용을 비교합니다. 876,100개 관측 행에 비해 comp2 고장은 259건이므로 겹치는 시간별 라벨을 독립 고장 사례처럼 해석하지 않습니다.
- horizon과 경고 확률 임계값은 검증 구간에서 선택하고 마지막 테스트 구간에서 평가합니다. 고장 후 수리, 정기교체, 재고 보유 정책 등을 같은 조건의 비교 기준으로 둡니다.
- 전체 센서 관측기간이 약 1년이라 90일 horizon에서는 사용 가능한 학습·평가기간이 많이 줄어듭니다. 처음부터 긴 기간의 높은 성능을 약속하지 않습니다.

달력 날짜와 교체·고장 이벤트가 함께 있다는 점에서 이 데이터는 제안한 조달 의사결정 실험에 구조적으로 맞습니다. 가속 수명시험 데이터를 실제 공장의 조달 일수로 환산하려면 별도의 시간 변환 가정이 필요합니다.

## 팀원 다운로드 재현

실제 사용한 배포본은 [Kaggle Microsoft Azure Predictive Maintenance](https://www.kaggle.com/datasets/arnabbiswas1/microsoft-azure-predictive-maintenance)입니다. 기존 Azure Blob 주소는 이번 환경에서 DNS 조회에 실패했습니다. 로컬 원본은 약 80.4 MB이며 Git에서 제외되므로 팀원은 별도로 다운로드합니다.

저장소 루트의 PowerShell에서 다음을 실행합니다. 기존 CSV를 덮어쓰지 않으며, 원본 파일과 추출 ZIP은 `.gitignore` 적용 대상입니다.

```powershell
New-Item -ItemType Directory -Force tmp, data/raw/azure_pdm | Out-Null
curl.exe -L --fail --show-error 'https://www.kaggle.com/api/v1/datasets/download/arnabbiswas1/microsoft-azure-predictive-maintenance' -o tmp/azure_pdm.zip
if ($LASTEXITCODE -ne 0) { throw '다운로드 실패' }
Expand-Archive -LiteralPath tmp/azure_pdm.zip -DestinationPath data/raw/azure_pdm
Get-FileHash data/raw/azure_pdm/*.csv -Algorithm SHA256
```

배포본은 향후 바뀔 수 있습니다. 해시가 기록된 검사 결과와 다르면 버전과 내용을 확인합니다. 데이터 라이선스·재배포 조건은 아직 확인되지 않았으며 Microsoft 코드 저장소의 라이선스를 Kaggle 데이터에 자동 적용하지 않습니다. 현재는 CSV 다운로드·기본 검사와 설계 설명까지 완료했으며 모델 학습이나 비용 시뮬레이션을 실행한 상태는 아닙니다.
